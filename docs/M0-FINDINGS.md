## 1. M0-1 — HwndHost 임베딩 ✅

`HwndHost.BuildWindowCore` 에서 `"static"` 클래스로 자식 창을 만들고, 그 HWND 를 mpv 의 `wid` 옵션으로
넘기는 방식이 문제없이 동작했다. 별도 창 클래스를 등록할 필요가 없었다.

```
자식 HWND        0x12159A
current-vo       gpu
dwidth×dheight   1280×720
hwdec            d3d11va
위치             00:00:12.000  f#720
드랍 프레임      0
```

**렌더링은 속성만으로 확인할 수 없으므로** `screenshot-to-file … window` 로 VO 출력을 뽑아 확인했다.
화면에 번인된 `F 720 / T 00:00:12.000` 과 엔진이 보고한 `f#720 / 00:00:12.000` 이 일치했다 —
속성 읽기가 아니라 **실제 표시된 프레임과의 교차 검증**이다.

> DPI 변경 · 멀티모니터 이동 · 전체화면 전환은 아직 확인하지 않았다. M1에서 확인한다.

## 2. M0-2 — 프레임 스텝 ✅

세 가지 프레임레이트 전부에서 **정방향 10회 → 역방향 10회 왕복 후 시작 프레임으로 정확히 복귀**했다.
중간 단계마다 Δ가 정확히 ±1인지도 검사했고 어긋난 건이 없다.

| 클립 | 시작 | 정방향 10회 | 역방향 10회 | 누적 오차 |
|---|---|---|---|---|
| 60fps CFR | f#600 | f#610 (Δ+10) | f#600 | **0** |
| 30fps CFR | f#300 | f#310 (Δ+10) | f#300 | **0** |
| 59.94fps CFR | f#600 | f#610 (Δ+10) | f#600 | **0** |

**이것이 엔진 선택의 결정적 근거다.** `frame-back-step` 은 libmpv 고유 기능이며,
LibVLCSharp 으로는 "현재 시각 − 1/fps 로 시크" 에뮬레이션이 불가피하다. 위 왕복 테스트를
에뮬레이션으로 통과시키기는 어렵다. ([SPEC §4.1](../SPEC.md#41-재생-엔진-비교))

## 4. M0-4 — A/V 오프셋 ✅ (범위) / 🟡 (청감)

`audio-delay` 속성으로 **−1000ms ~ +1000ms 전 구간을 1ms 오차 없이 왕복**했다.
FR-401의 범위와 단위를 그대로 만족한다. 재인코딩 없이 속성 하나로 끝나므로 구현 부담이 없다.

```
  -1000 ms →  -1000.0 ms  ✓        +5 ms →     +5.0 ms  ✓
   -333 ms →   -333.0 ms  ✓       +33 ms →    +33.0 ms  ✓
    -33 ms →    -33.0 ms  ✓      +500 ms →   +500.0 ms  ✓
      0 ms →      0.0 ms  ✓     +1000 ms →  +1000.0 ms  ✓
```

**남은 확인**: 재생 중 값을 바꿀 때 끊김이나 팝 노이즈가 없는지는 청감 확인이 필요하다.
`avsync_1s_flash_click.mp4` (1초마다 흰 플래시 + 동시 클릭음)로 확인한다.
클립 자체는 검증했다 — 플래시는 정확히 0.000/1.000/2.000…초, 무음 구간 −91dB / 클릭 −14.3dB.

## 5. M0-5 — 정확 시크 ✅

| 클립 | 시크 왕복 평균 | 최대 | NFR-03 (150ms) |
|---|---|---|---|
| 60fps | 30.4ms | 49.0ms | 충족 ✓ |
| 30fps | 44.6ms | 66.4ms | 충족 ✓ |
| 59.94fps | 34.8ms | 57.7ms | 충족 ✓ |

위치 정확도는 5개 목표 지점 전부 1프레임 이내였다. 주목할 동작:

```
  8.125s →  8.1333s   오차 +8.3ms  ✓
```

8.125초는 60fps에서 프레임 경계가 아니다(487.5번째). mpv 는 **해당 시각을 포함하는 프레임(488)으로
스냅**했고, 이것이 올바른 동작이다. UI에서 "요청한 시각"과 "실제 위치"가 다르게 보일 수 있으므로,
북마크 저장 시에는 **스냅된 실제 위치를 저장**해야 왕복이 맞는다. (FR-321 구현 시 주의)

## 6. M0-6 — 재생 중 앱 단축키 차단 ✅

### 판정 로직 — 테스트 298개 통과

`src/OtogeTrainer.Input/InputGate.cs` 는 SPEC §6.3 의 판정 순서를 그대로 옮긴 순수 함수다.

| 테스트 | 고정하는 결정 |
|---|---|
| `재생_중_통과하는_키는_ESC_뿐이다` | **D-4 (예외 없음)** — `Key` enum 전체 중 재생 중 통과하는 키가 ESC 하나뿐임을 확인 |
| `D4_예외로_거론됐던_키도_재생_중_차단된다` | `F11` `F` `M` `Add` `T` 전부 차단 |
| `ESC는_재생_여부와_무관하게_Escape로_판정된다` | **D-3** |
| `텍스트_입력_중에는_무조건_통과시킨다` | **FR-509** |
| `Alt_F10_계열도_재생_중_차단된다` | **§6.2-6** `Key.System` 래핑 |
| `모든_키에_대해_판정_순서가_지켜진다` | 판정 순서 불변식 (키가 추가돼도 유지) |

### 설계상 확정된 것

**포커스 억제는 재생 중에만 건다.** 처음에는 가드 토글에 연동했으나, 그러면 일시정지 상태에서도
`Tab` 이 죽어 NFR-11(모든 기능에 키보드 경로)이 깨진다. 실제 완화책은 두 가지다.

- 재생 진입 시 **`Keyboard.Focus(window)`** — 포커스를 컨트롤에서 떼어 내되 창이 키를 계속 받게 한다
- 재생 중에만 `KeyboardNavigation.TabNavigation` / `DirectionalNavigation` = `None`

컨트롤 바 버튼에 `Focusable=false` 를 영구 적용하는 방안은 일시정지 상태의 키보드 접근성을
해치므로 채택하지 않았다.

### 남은 확인 (수동)

단위 테스트는 "우리 코드가 무엇을 반환하는가"만 본다. 실제 사고는 WPF 기본 동작에서 나므로
하네스(`dotnet run --project spike/OtogeTrainer.M0`)에 누출 경로를 깔아 두고 자동 검출하게 했다.

| 검출기 | 대응 누출 경로 |
|---|---|
| 버튼이 마우스 없이 `Click` 발생 | §6.2-2 포커스된 버튼을 Space/Enter가 누름 |
| 슬라이더가 마우스 없이 `ValueChanged` | §6.2-3 방향키가 Slider 값을 움직임 |
| 재생 중 키보드 포커스 이동 | §6.2-4, §6.2-5 방향 탐색 · Tab 순회 |
| `WM_INITMENU` / `WM_SYSCOMMAND(SC_KEYMENU)` | §6.2-6 Alt·F10 시스템 메뉴 |
| 의도치 않은 재생 중단 | §6.2-1 단축키 발동 |

**"입력 가드 사용" 체크를 끄면 대조군으로 같은 조작에서 누출이 재현된다.** 가드 ON에서 0건,
OFF에서 검출되면 각 완화책이 실제로 필요했음이 확인된다.

### 발견된 누출 1건 — `Alt` 단독이 시스템 메뉴를 엶 (§6.2-6)

수동 확인 중 **가드가 켜진 상태에서도 `Alt` 단독 입력이 창 시스템 메뉴를 여는 것**이 검출됐다.
하네스가 잡아낸 유일한 진짜 결함이며, 설계 문서의 대응책이 틀렸던 항목이다.

**원인**: 시스템 메뉴는 라우팅 이벤트가 아니라 `DefWindowProc` 이 `WM_SYSCOMMAND(SC_KEYMENU)` 를
처리하면서 열린다. `PreviewKeyDown` 에서 `e.Handled = true` 로 소비해도 **메뉴는 그대로 열린다.**
SPEC §6.2-6 에 "`e.SystemKey` 로 판정 후 소비" 라고만 적어 둔 것이 불충분했다.

**수정**: `HwndSource.AddHook` 으로 메시지 단계에서 잘라낸다. 단, `lParam` 이 0 인 경우
(= `Alt`/`F10` 단독)만 차단하고, `Alt+Space` 처럼 문자가 붙은 조합은 윈도우 기본 동작이므로
통과시킨다(FR-502).

**회귀 테스트**: `--inputtest` 로 자동화했다.

```
가드 OFF (대조군)  누출 1건  ✓ 경로 재현됨
가드 ON            누출 0건  재생 유지 True  ✓ 차단됨
```

대조군을 함께 확인하는 이유는, 가드 ON 에서 0건이 나온 것이 **차단에 성공해서인지 테스트가
애초에 그 경로를 못 건드려서인지** 구분하기 위해서다.

### 함께 고친 것 — 재생 엔진 검증 창에 가드가 없었음

재생 엔진 검증 창(`PlaybackWindow`)에는 입력 게이트를 붙이지 않아, 재생 중 `Space`/방향키가
그대로 WPF 컨트롤에 먹혔다. M0-7(“mpv 가 키를 먹는지”)을 판단할 수 없는 상태였다.

키를 만지는 코드를 `WindowInputGuard` 하나로 모아 두 창이 같은 경로를 쓰게 했다.
SPEC R7(진입점 단일화)이 문서상의 원칙이 아니라 실제로 지켜야 할 이유가 여기서 드러났다.

### 발견된 누출 2건 — `ClearFocus()` 가 ESC 까지 죽임 (§6.2-2)

첫 수정 직후 **ESC 가 먹지 않아 일시정지가 불가능하다**는 보고를 받았다.

**원인**: 포커스를 컨트롤에서 떼어 내려고 `Keyboard.ClearFocus()` 를 썼는데, 포커스가 `null` 이 되면
키 이벤트가 라우팅될 대상이 사라져 **`Window.PreviewKeyDown` 자체가 발생하지 않는다.**
게이트가 ESC 를 삼킨 것이 아니라, 게이트까지 오지도 못한 것이다.

**증상이 정상처럼 보인다는 점이 가장 위험했다.** "다른 키는 잘 막히는데 ESC만 안 된다" 로
관측되지만, 실제로는 아무것도 차단하고 있지 않았고 전부 소실되고 있었다. 하네스의 자동
검출기(버튼/슬라이더/포커스)도 전부 조용했다 — 애초에 이벤트가 없으니 누출도 없었던 것.

**수정**: `Keyboard.Focus(window)`. 창 자신이 포커스를 가지면 컨트롤에서는 떼어 내면서
키 이벤트는 계속 받는다.

**회귀 테스트**: 이 버그를 잡는 결정적 단서는 "일시정지 중 Space 도 안 먹는다" 였다.
그래서 `--inputtest` 에 **포커스가 살아 있는지**를 직접 검사하는 항목을 넣었다.

```
FR-504  재생 중에도 키 이벤트가 창에 도달해야 한다
  ✓ 재생 중 키보드 포커스가 살아 있는가          FocusedElement = MainWindow
  ✓ 포커스가 컨트롤이 아닌 창에 있는가 (§6.2-2)   MainWindow
```

또한 키 입력 검증을 `PostMessage` 에서 **WPF 라우팅 이벤트 직접 발생**으로 바꿨다.
PostMessage 로 보낸 키는 창이 실제 포그라운드 포커스를 갖지 못하면 WPF 가 무시해서,
스크립트 실행 시 결과를 신뢰할 수 없었다. Alt 시스템 메뉴만 Win32 경로이므로 PostMessage 를 유지한다.

부수적으로, 가드가 `e.IsDown`("그 키가 지금 물리적으로 눌려 있는가") 대신
`e.RoutedEvent == Keyboard.PreviewKeyDownEvent`("이게 누름 이벤트인가")로 판정하도록 고쳤다.
의미가 미묘하게 다르고, 후자가 우리가 실제로 알고 싶은 것이다.

### 하네스와 제품의 차이 — 키 로그

하네스는 모든 키의 판정 결과를 화면에 찍는다. **제품에서는 그러면 안 된다.**
SPEC §6.3 은 재생 중 삼킨 키를 "로그도 남기지 않고 조용히 버린다" 로 규정한다 —
판정은 O(1) 이어야 하고(NFR-05), 키 입력 내용을 저장하지 않아야 하기 때문이다(NFR-12).

하네스가 로그를 남기는 이유는 진단 때문이다. **"삼켰다" 와 "이벤트가 도달하지 않았다" 는
겉보기가 같다.** 위 ClearFocus 버그가 정확히 그 함정이었고, 판정 결과가 찍히는지로만
구분할 수 있었다. 하네스 로그도 메모리에만 남으며 파일로 나가지 않는다.

`MainWindow.Log` 에 "제품으로 옮기지 말 것" 주석을, 로그 패널에 같은 취지의 안내를 달아 두었다.

### 수동 검증 결과 (2026-09-15)

3회에 걸쳐 확인했고, **그 과정에서 결함 3건이 나왔다.**

| 회차 | 보고 | 결과 |
|---|---|---|
| 1 | "Alt 키 입력 시 누출 감지됨" · "재생 엔진 창에서 Space·화살표가 그냥 입력됨" | 결함 2건 — §6.2-6 대응책 부족, `PlaybackWindow` 가드 누락 |
| 2 | "다른 키는 잘 막히는데 ESC까지 막혀서 일시정지가 안 됨" | 결함 1건 — `ClearFocus` 로 키 이벤트 소실 |
| 3 | "이제 다 잘 작동됩니다" | **통과** |

**M0 가 실제로 값을 한 지점이다.** 자동 검증 항목이 전부 통과한 뒤에도 손으로 만지자
결함 3건이 나왔고, 그중 둘은 **설계 문서의 대응책 자체가 틀렸던** 것이다.
자동 검증만 믿고 M1 에 들어갔다면 구현 도중에 같은 함정을 다시 밟았을 것이다.

#### 항목별 근거

ROADMAP §3.3 체크리스트를 근거별로 나눠 정리한다.

**① 자동 회귀 테스트로 고정됨** — `--inputtest`, 실행할 때마다 재검증된다

- 재생 중 `Space` `←` `→` `1` `F11` `M` `T` 난타 → 재생 유지
- `ESC` → 즉시 일시정지
- 일시정지 중 `ESC` → 아무 일도 하지 않음 (D-3)
- 일시정지 중 `Space` → 재생 시작
- `Alt` 단독 → 시스템 메뉴 차단 (가드 OFF 대조군에서 누출 재현 확인)
- 재생 중 키보드 포커스 생존 및 창 보유 (§6.2-2)

**② 수동 확인됨** — 3회차 총평에 근거. 개별 항목을 따로 보고받은 것은 아니다

- 컨트롤 바 버튼 클릭 직후 `Space` → 버튼 재활성화 없음 (§6.2-2)
- 타임라인 슬라이더 조작 직후 `←` → 값 변화 없음 (§6.2-3)
- `Tab` 연타 → 포커스 순회 없음 (§6.2-5)
- 영상 영역 포커스 상태에서 키 입력 → mpv 기본 바인딩 발동 없음 (M0-7, §7)

**③ 미확인 — M1 에서 확인해야 함**

| 항목 | 이유 |
|---|---|
| 텍스트 입력 중 `Space`·방향키 (FR-509) | **하네스에 텍스트 입력 컨트롤이 없어 손으로 확인할 수 없었다.** 단위 테스트로만 덮여 있다 |
| 재생 중 컨트롤 바로 전체화면·음소거·볼륨·항상 위 도달 (R7) | 하네스의 해당 버튼은 누출 검출용 더미다 |
| 키보드 미디어 볼륨 키 → 시스템 볼륨 변경 | 하네스 범위 밖 |
| 설정 "재생 중에도 단축키 허용" ON (FR-508) | 게이트 로직은 단위 테스트로 덮였으나 UI 경로는 미확인 |
| 앱 비활성/최소화 후 복귀 시 일시정지 상태 (FR-507) | 미보고 |
| `Alt+Space` → 창 시스템 메뉴 정상 개방 (FR-502) | 차단 대상에서 제외했으나 실제 개방은 미확인 |
| 전역 무영향 (`Alt+Tab` 후 메모장 타이핑, `Win` 키) | 전역 후킹을 쓰지 않으므로 구조상 영향이 없으나 미확인 |

③ 중 **FR-509 가 가장 신경 쓰인다.** 판정 순서 1번이라 틀리면 북마크 라벨에 스페이스를
못 치는 수준의 문제가 되는데, 하네스에 입력 컨트롤이 없어 실물로 확인하지 못했다.
M1 에서 북마크 라벨 UI 를 만들 때 최우선으로 확인한다.

## 7. M0-7 — libmpv 키 소비 ✅

`--input-default-bindings=no`, `--input-vo-keyboard=no` 를 초기화 옵션으로 설정했고
([SPEC §4.3](../SPEC.md#43-libmpv-초기화-옵션-핵심)), 재생 엔진 검증 창에서 수동으로 확인했다.
영상 영역에 포커스를 준 상태로 키를 눌러도 mpv 기본 바인딩(일시정지 · 시크 · 볼륨)이 발동하지 않는다.

> 다만 처음에는 **판정 자체가 불가능한 상태였다.** `PlaybackWindow` 에 입력 가드를 붙이지 않아
> WPF 컨트롤이 키를 먼저 먹었기 때문이다. mpv 가 키를 먹는지 보려면 그 앞단이 조용해야 한다는
> 것을 놓쳤다. 가드를 붙인 뒤에야 의미 있는 확인이 됐다.

## 8. M0-8 — VFR ⏸

합성 클립 3종은 전부 CFR 이므로 `container-fps` 와 `estimated-vf-fps` 가 일치했다
(60/60, 30/30, 59.94/59.94). 하네스는 두 값이 1.0 이상 벌어지면 `⚠ VFR 의심` 을 띄운다.

**실제 OBS/게임바 캡처 영상이 있어야 판정할 수 있다.** VFR 은 합성으로 재현하기 어렵다.
1080p/4K, H.264/HEVC 가 섞인 실제 플레이 영상 5~10개가 필요하다. (SPEC R1)

## 라이선스 메모 (D-6 연동)

사용한 `mpv-dev-x86_64` 빌드의 구성은 **확인하지 않았다.** 일반 배포되는 mpv-dev 빌드는
GPLv2+ 구성인 경우가 많다.

[D-6](DECISIONS.md#d-6-라이선스--공개-방침) 결정에 따르면 최종적으로는 LGPL 구성 빌드가 필요하지만,
**M0 스파이크는 배포하지 않으므로 검증 자체에는 지장이 없다** — GPL 의무는 배포 시점에 발생한다.
구성 확인은 배포 준비 시점(M1 이후)의 과제로 [ROADMAP §6](ROADMAP.md#6-구현-착수-전-체크리스트)에 남겨 두었다.
