## 3. 검증 중 발견한 결함

### 3-1. 프레임 스텝 유실 — 역방향 연속 스텝의 대부분이 사라짐 ⚠ 가장 중요

첫 종단 검증에서 "프레임 +1" 이 실패했다. 진단해 보니 두 경로에서 스텝이 버려지고 있었다.

| 조작 | 결과 |
|---|---|
| 점프 직후 0ms 에 스텝 | **무시됨** (50ms 뒤부터는 먹음) |
| 정방향 5연속 | +5 정상 |
| **역방향 5연속 (0ms 간격)** | **−1 만 반영** |
| **역방향 5연속 (25ms 간격)** | **−2 만 반영** |

**원인**: mpv 는 시크가 진행 중일 때 들어온 프레임 스텝을 버린다. `frame-back-step` 은 내부적으로 **시크**라서, 연달아 보내면 앞선 역스텝의 시크 위에 겹쳐 유실된다. `playback-time` 속성은 목표 위치를 즉시 보고하므로 겉으로는 시크가 끝난 것처럼 보인다.

**영향**: 우클릭 드래그로 프레임을 되감아 찾는 동작이 정확히 이 경우다. 앱의 핵심 조작이 **조용히 절반만 먹는** 결함이었다.

**M0 에서 못 잡은 이유**: M0-2 검증은 스텝마다 프레임 변화를 기다린 뒤 다음 스텝을 보냈다. 사람이 쓰는 속도로는 보내지 않았다.

**수정**: 엔진에 스텝 큐를 두고, 이전 시크가 끝난 것을 확인한 뒤 다음 스텝을 보낸다. 끝난 것의 판정에는 둘 다 필요하다.

- `PLAYBACK_RESTART` 이벤트만 보면 — 합쳐지지 않은 앞선 시크의 재시작에 속는다
- `seeking` 속성만 보면 — 명령 직후 시크가 아직 실행되기 전이라 `false` 로 읽힌다

시크는 최근 의도가 이긴다: 스텝이 쌓인 상태에서 점프하면 남은 스텝은 버린다. 빠른 드래그 뒤 한참 따라오지 않도록 큐는 ±30 에서 자른다.

**테스트의 함정도 있었다**: 처음 실패했을 때 바로 뒤의 "프레임 −1 로 복귀" 는 **애초에 안 움직였기 때문에 공짜로 통과**했다. 왕복 · 연속 스텝의 Δ 로 판정하도록 다시 짰다.

### 3-2. 일시정지 중 Space 가 두 번 처리됨

입력 가드가 일시정지 상태에서 처리한 단축키를 소비(`e.Handled`)하지 않았다. 버튼에 포커스가 있으면 `Space` 가 **단축키와 버튼 클릭을 둘 다** 일으켜 재생 토글이 두 번 = 아무 일도 없었다.
처리한 단축키는 누름·뗌 둘 다 소비하도록 고쳤다(`ShortcutHandler` 가 `bool` 을 돌려줌).

### 3-4. 창을 닫으면 예외 발생 — 첫 수동 사용에서 발견

앱을 띄워 두자마자 닫는 순간 "예상하지 못한 오류" 대화상자가 떴다. 크래시 로그:

```
System.InvalidOperationException: 창을 닫는 중에는 … Close … 을(를) 호출할 수 없습니다.
   at OtogeTrainer.App.MainWindow.OnClosing
```

**원인**: 닫기 전에 위치·썸네일을 저장하려고 `Closing` 을 취소하고, 저장이 끝나면 `Close()` 를 다시 부른다.
**라이브러리 화면에서는 저장할 것이 없어 저장이 동기로 끝나므로**, `await` 뒤의 `Close()` 가 아직 `Closing`
처리 도중에 실행됐다. 플레이어 화면에서 닫으면 저장이 실제로 비동기라 드러나지 않는다.

**자동 검증이 놓친 이유**: 종단 검증은 창을 닫지 않았다(닫으면 앱이 종료되어 검증이 끝나므로).
이 경로를 "수동 확인 목록" 에 올려 두었고, 실제로 거기서 나왔다.

**수정**: `Dispatcher.BeginInvoke(Close)` 로 `Closing` 이벤트가 끝난 뒤에 닫는다.

**회귀 테스트**: 종단 검증 10단계. 검증 중에는 `ShutdownMode` 를 명시적 종료로 바꿔 창이 닫혀도 검증이 계속되게 하고,
예외 대화상자 대신 크래시 로그 증가 여부로 판정한다. **수정 전 코드로 되돌려 같은 예외가 재현되는 것(대조군)을 확인한 뒤** 수정을 적용했다.

### 3-5. 재생 바를 클릭해도 이동하지 않음 — 수동 사용에서 발견

재생 바의 다른 위치를 클릭해도 이동하지 않았다(재생 중 · 일시정지 중 모두). 종단 검증에 **창으로 실제 마우스 메시지를 보내는 재현 단계**를 먼저 넣어 4건 모두 실패하는 것을 확인한 뒤 고쳤다. 원인은 둘이었다.

1. **처리기가 불리지 않음.** 스크럽 시작 처리기를 XAML 이벤트 속성으로 걸었는데, `Slider` 는 트랙 클릭을 자기 클래스 처리기에서 "처리됨" 으로 표시하고 클래스 처리기는 인스턴스 처리기보다 먼저 돈다. 슬라이더 값만 잠깐 바뀌었다가 30Hz 갱신이 원래 위치로 되돌렸다. → `handledEventsToo` 로 등록.
2. **재생 중 클릭 위치가 틀어짐.** 1을 고치자 일시정지 중에는 맞는데 재생 중 40% 클릭이 20% 로 갔다. 슬라이더가 받은 좌표는 정확했다(x=374, 목표 374). `Track.ValueFromPoint` 가 절대 위치가 아니라 **마지막 레이아웃 시점의 썸 중심**으로부터의 거리로 계산하는데, 재생 중에는 값이 계속 바뀌어 썸 위치가 한 박자 늦고, 캡처 직후의 이동 이벤트에서 오차가 한 번 더 누적됐다(60s → 35.75s → 23.54s 로 로그와 정확히 일치). → 트랙 폭에서 비율을 직접 계산.

함께 바꾼 것: 트랙 **아무 데서나 눌러 끌기**(기존엔 썸을 잡아야만 끌 수 있었다), **끄는 도중 영상이 따라옴**(80ms 간격 미리보기 시크, 놓을 때 정확 시크 한 번 더). 초안(UI-BLUEPRINT §4)의 "놓을 때만 시크" 에서 바뀐 것이다.

**테스트 쪽 함정**: 처음엔 일시정지 중 75% 클릭이 120s 로 판정됐다. WPF 는 마우스 *이동* 메시지는 메시지 좌표를 쓰지만 *버튼* 메시지에서는 실제 커서 위치를 읽어서, 메시지만 보내면 사용자 커서가 있던 곳을 누른 것이 된다. 검증 중에는 커서를 그 자리로 옮기고, 끝나면 원래 자리로 돌려놓는다.

### 3-3. 배속 프리셋이 `1`, `2` 로 표시됨

화면 캡처로 발견. `Button.Content` 는 `object` 라 바인딩의 `StringFormat` 이 무시된다(문자열 대상에만 적용). `ContentStringFormat` 으로 고쳤다.

## 4. 영상 위 마우스 입력 — 설계 결정

> **§7 에서 바뀌었다.** 아래는 M1 첫 구현 기록이다. 영상 위 마우스 *제스처*는 D-8 로 제거됐지만,
> **mpv 자식 창 비활성화는 그대로 유지한다** — 영상을 클릭해도 포커스가 넘어가지 않아야 ESC 와 재생 중 동작 키가 먹기 때문이다.

재생 중에는 키가 전부 막히므로(D-4) 마우스가 유일한 조작 경로다. UI 를 올리기 전에 먼저 검증했다.

**문제**: mpv 는 `wid` 로 넘긴 창 안에 **자기 스레드의** 자식 창을 만들어 그린다. 그대로 두면 영상 위 입력이 전부 그 창으로 가 WPF 가 클릭을 받지 못하고, 클릭 한 번에 키보드 포커스가 넘어가 **ESC 가 먹지 않게 된다** — M0 의 `ClearFocus` 버그와 같은 증상이 다른 경로로 재발하는 것이다.

**결정**: mpv 자식 창을 비활성화한다. 비활성 창은 입력을 받지 않고 `WindowFromPoint` 도 건너뛰어, 마우스 메시지가 부모인 표면 창으로 떨어진다.

```
엔진 창 스레드   UI 와 다름 (우려 확인)
대조군(활성)     중앙 히트 → mpv 창      표면 도달 False
비활성화 후      중앙 히트 → 표면 창     표면 도달 True
렌더링           비활성화 후 F 1200 / T 00:00:20.000 정상
```

처음엔 `WM_PARENTNOTIFY` 훅이 이미 비활성화해 버려 "비활성화 전" 값이 대조군 역할을 못 했다. 활성화를 되돌려 입력이 실제로 mpv 창으로 가는 것을 먼저 보인 뒤 비활성화 효과를 확인했다.

**결과로 바뀐 UI**: 영상 위에는 WPF 요소를 겹칠 수 없다(airspace). OSD 와 컨트롤 바는 **영상 바깥 레이아웃**에 둔다. [UI-BLUEPRINT §4 · §5](UI-BLUEPRINT.md) 에 반영.

### 단축키 ↔ 마우스 경로 대조 (R7) — ⚠ D-8 이전 기록, 현행은 §7

## 7. D-8 반영 — 영상 위 마우스 조작 제거와 재생 중 동작 키

**2026-09-16, M1 수동 사용 중 사용자 요청.** 결정 근거는 [DECISIONS D-8](DECISIONS.md#d-8-영상-위-마우스-조작-없음--재생-중-동작-키).

> 클릭 입력이 작동하긴 하지만, 마우스를 쓰는 리듬게임이 있어 영상을 건드렸을 때 뭔가 작동되면 안 된다.
> 대신 마우스에 매핑되어 있던 기능은 F1~F12 중 단축키로 두고, 설정에서 ESC 를 제외한 아무 키로 바꿀 수 있게.

### 바뀐 것

| 영역 | 변경 |
|---|---|
| `VideoSurfaceHost` | 제스처 인식(클릭 · 휠 · 우클릭 드래그 · 사이드 버튼) **삭제.** 모든 마우스 메시지를 받아 버린다. 누름 순간 포커스 회수 알림만 남김 |
| mpv 자식 창 비활성화 | **유지.** 클릭 시 포커스가 mpv 창으로 넘어가면 ESC 도 재생 중 동작 키도 먹지 않는다 |
| `InputGate` | 판정 순서에 "재생 중 동작 키" 추가 (ESC 다음, 재생 중 차단 앞) |
| `PlaybackKeyMap` (신규) | 동작 7개 ↔ 키. 맞바꿈 · 해제 · 기본값 · 수정자 규칙 · 손상된 설정 복구 |
| `WindowInputGuard` | 키 배치 조회, IME · Dead key 래핑 해제, Alt/F10 을 지정했을 때 시스템 메뉴 차단 |
| 설정 창 (신규) | 동작별 키 입력 대기 · 해제 · 기본값. 변경 즉시 `settings.json` 저장(임시 파일 후 교체) |
| 플레이어 | 하단에 현재 재생 중 동작 키를 앰버색으로 항상 표시 · ⚙ 설정 버튼. 툴팁에서 마우스 안내 제거 |

### 검증

- **단위** — `PlaybackKeyMap` 20여 개(기본 배치에 F10~F12 없음, 맞바꿈, 수정자 규칙, 손상 · 중복 설정 복구), 게이트 전수 조합에 "재생 중 동작 키" 차원 추가.
  기존 "재생 중 통과하는 키는 ESC 뿐" 은 **"ESC 와 F1~F7 뿐"** 으로 갱신 — D-4 를 고정하던 테스트가 D-8 을 고정하게 됐다.
- **종단** — §2 의 5 · 5-2 · 5-3 단계.
  "영상 위 마우스 무동작" 은 **아무 일도 없었음** 을 확인하는 검사라, 메시지가 유실돼서 조용했던 것과 구별해야 한다. 표면이 누름을 실제로 받았는지(`PointerPressed` 4회)를 대조로 함께 센다. 같은 메시지로 D-8 이전에는 재생 · 이동이 일어났던 것이 직전 버전의 검증 결과다.
- **화면** — 설정 창 캡처로 배치 확인. 처음 캡처가 오른쪽이 잘려 보였는데, 창 내용의 Margin 만큼 밀려 찍힌 캡처 쪽 문제였다(창 템플릿 최상위를 찍도록 수정).

### 이 변경으로 남은 확인

§6 수동 확인 목록에 반영했다. 특히 **키 자동 반복**(누르고 있기)은 합성 키 이벤트로 흉내 낼 수 없어 자동 검증하지 못했다.
